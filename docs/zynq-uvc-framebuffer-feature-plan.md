# Feature Plan: Zynq UltraScale+ (XCZU19EG) Framebuffer to USB 3.0 UVC Camera

## Goal
Expose video generated by the PL pipeline (stored in PS DDR framebuffer) as a **single USB UVC camera** to a host PC, with:

- Resolution/framerate target: up to **1080p30**
- Format target: **YUY2**
- End-to-end latency target: **< 100 ms**
- Interop targets: **Microsoft Teams, OBS, WebRTC browsers**

## Confirmed Constraints and Inputs
- USB 3.0 is available on the platform.
- Device should enumerate as a single UVC camera function.
- Input framebuffer format is RGB 4:4:4, triple-buffered.
- Video producer is a PL pipeline.
- CPU budget available for this feature: up to 60%.
- Kernel/device tree changes are allowed.
- No privacy LED / mute / extra controls are required.

## Proposed Architecture

1. **Video Source (PL -> PS DDR)**
   - PL writes RGB 4:4:4 frames into triple-buffered framebuffer in PS memory.
   - Metadata required per frame: width, height, stride, buffer index, timestamp.

2. **Capture + Conversion Service (userspace daemon)**
   - A dedicated service acquires completed framebuffer buffers.
   - Converts RGB 4:4:4 -> YUY2.
   - Maintains a small ring of UVC output buffers (3-6) for pacing and jitter tolerance.
   - Timestamps frames and enforces 30 FPS pacing.

3. **USB UVC Gadget Layer**
   - Linux USB gadget stack (configfs + UVC function) in USB 3.0 device mode.
   - Single UVC streaming interface with YUY2 at required modes.
   - Expose `/dev/videoX` gadget endpoint to host.

4. **Host Interoperability Validation**
   - Validate with Teams, OBS, and browser WebRTC getUserMedia flows.
   - Verify stable enumerate/open/stream/reconnect cycles.

## Implementation Plan (Phased)

### Phase 0 - Platform Bring-up (1 week)
- Confirm DWC3/device-tree USB role configuration for stable SuperSpeed gadget mode.
- Build kernel with required gadget/UVC options:
  - `CONFIG_USB_CONFIGFS`
  - `CONFIG_USB_F_UVC`
  - DWC3 gadget/device-mode options
- Stand up a static UVC test stream to host (no framebuffer integration yet).

**Exit criteria**
- Host detects camera consistently over USB 3.0.
- Sustained streaming session >= 30 minutes without disconnect.

### Phase 1 - Functional Framebuffer Streaming (1-2 weeks)
- Implement framebuffer reader for triple-buffer handoff from PL producer.
- Integrate RGB->YUY2 conversion path.
- Stream 720p30 and 1080p30 through UVC gadget.

**Exit criteria**
- Live PL video is visible as webcam stream.
- Basic frame pacing and recovery from brief host-side stalls.

### Phase 2 - Latency + Performance Optimization (1-2 weeks)
- Profile CPU and memory bandwidth for conversion path.
- Optimize conversion implementation (SIMD/NEON, threading, cache-friendly line traversal).
- Tune buffering to hold latency < 100 ms under nominal load.

**Exit criteria**
- 1080p30 stable with CPU <= 60% for capture/convert/stream pipeline.
- End-to-end latency consistently < 100 ms.

### Phase 3 - Interop and Hardening (1-2 weeks)
- Interop matrix validation: Teams, OBS, Chromium/Edge/Firefox WebRTC.
- Soak testing (multi-hour runs, cable reconnects, host sleep/wake, app restart).
- Production integration: systemd service, logging, startup ordering, failure restart policy.

**Exit criteria**
- Pass interop matrix.
- No critical defects in soak test.

## Performance and Bandwidth Considerations

- 1080p30 YUY2 payload:
  - 1920 x 1080 x 2 bytes x 30 fps ~= 124 MB/s (~995 Mb/s payload before protocol overhead).
- This is generally appropriate for USB 3.0, but not reliable for USB 2.0 HS.
- RGB->YUY2 conversion is the dominant CPU task; optimization is critical to stay under 60% CPU budget.

## Key Technical Decisions

1. **Zero-copy vs copy path**
   - Preferred: DMA-BUF/DRM-compatible buffer sharing from producer to streamer where feasible.
   - Fallback: userspace copy from mapped framebuffer.

2. **Frame drop policy**
   - Favor low latency by dropping stale frames when host or conversion path lags.
   - Never allow queue growth to violate 100 ms target.

3. **Clocking strategy**
   - Stream at fixed 30 FPS cadence.
   - Timestamp at acquisition and at UVC queue to track jitter and queueing delay.

## Estimated Difficulty

**Overall difficulty: Medium-High**

- USB gadget and UVC bring-up: Medium
- Framebuffer synchronization with PL triple buffering: Medium
- RGB->YUY2 conversion at 1080p30 within CPU budget: Medium-High
- Host app interoperability (Teams/OBS/WebRTC): Medium

**Estimated total effort:** ~4-7 weeks (single engineer) depending on existing board support maturity.

## Acceptance Criteria

1. Enumerates as one UVC camera on Windows/Linux hosts over USB 3.0.
2. Streams 1080p30 YUY2 from PL-backed framebuffer.
3. End-to-end latency remains < 100 ms in nominal operation.
4. Capture/convert/stream stack stays within 60% CPU budget target.
5. Demonstrated compatibility with Teams, OBS, and WebRTC browser capture.

## Open Questions

2. Is there a strict boot-time requirement for camera readiness (e.g., available within N seconds after power-on)?
